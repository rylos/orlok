# Orlok — Requirements (draft v0)

> Status: **draft, to be refined**. Stable IDs (`R-XXX-n`) so they can be referenced in issues and commits.
> Priority: **M** = MVP · **S** = phase 2 · **L** = later.

## 1. Vision

A **self-hosted** platform (one installation = one company, shipped with Docker) where a company creates
**offices** staffed by **virtual colleagues**. People, invited by email, work with the colleagues of their
offices from the web (desktop and mobile). Colleagues **remember** (a self-maintained office wiki) and
**act** for real on servers and PCs, with protected credentials, policies, approvals and a full audit trail.

Distributed as a product: an empty installation plus documentation, with the full guide on the
website (`rylos/orlok-web`). The first scenario it is built for is in §2.

## 2. First scenario: an IT office

- **Who**: the IT manager. Goal: virtual colleagues handle the company's IT requests even when the
  manager is away (holidays): they solve what the policies allow and ask for remote approval (mobile)
  for the rest.
- **Starting knowledge**: the office's existing notes (for example a Joplin notebook on infrastructure
  and business applications) → imported into the office wiki (R-MEM-11).
- **Technical scope**: virtualization cluster (Proxmox), firewall (pfSense), SQL Server and the ERP on
  it, file server and Windows domain, Docker server, printers and user PCs.
- **Initial colleagues**: helpdesk (first contact with users), Linux/Proxmox sysadmin, Windows/AD
  sysadmin, SQL Server DBA.
- **AI models**: any provider configured like the others (R-MOD-1), an Anthropic-compatible gateway on
  the company network included.
- **Email**: the company SMTP; Microsoft 365 Direct Send, for example, delivers only to recipients in
  the tenant, which is enough for internal invitations.

## 3. Glossary

| Term | Meaning |
|---|---|
| Installation | An Orlok instance for a single company |
| Office | Group holding people, virtual colleagues and their memory (the wiki) |
| Colleague | AI agent of one person, in one of their offices, with a role, instructions and a model profile; it works only for that person and never with more rights. The exception is the **office colleague**: one per office, set up by an administrator, there for everyone in the office and only reading its wiki (R-ADM-8) |
| Person | Human user, invited by email, member of one or more offices |
| Conversation | Chat thread between people and colleagues |
| Intervention | Tracked operational work (plan → approval → execution → report) |
| Host | Managed machine: **server** (agentless) or **client** (PC/laptop), in one registry for the installation. The account used on it is the credential of the person a colleague works for, not a property of the host |
| Credential | A person's own encrypted account (password, SSH key, token), used by the colleagues working for them on the hosts they chose |
| Wiki | The office's structured memory (linked markdown pages) |
| Model profile | A model and a mode (deny, ask, full access, yolo), granted to people by administrators |

## 4. Roles

| Role | Scope | Can |
|---|---|---|
| Administrator | Installation | everything: offices and their office colleagues, people, providers, global settings, audit; works in every office, so is assigned none |
| Office manager | Office | wiki editing and review of their office, filing documents with one of their own colleagues |
| Member | Office | create their own colleagues, talk with them and with the office colleague, approve the interventions asked for them |
| Observer | Office | read the office wiki (not enforced yet: today an observer works like a member) |

## 5. Functional requirements

### 5.1 Administration (ADM)
- **R-ADM-1 (M)** First-run wizard: creates the administrator, company name, first model provider.
- **R-ADM-2 (M)** Offices CRUD. An administrator can also empty the wiki of an office (pages with their history, documents, log, review queue; colleagues, conversations and synonyms stay) to import it again from scratch, after typing the office name; refused while a document is being read into it.
- **R-ADM-3 (M)** Personal colleagues: each person creates their own in one of their offices (name, role, system instructions, one of the profiles granted to them), and renames, archives or deletes them. Nobody else sees them, administrators included (the one exception is the office colleague, R-ADM-8). A colleague whose profile is taken away from its owner stops answering until another is chosen. Archiving hides it and keeps its conversations; deleting removes its conversations and instructions and cancels its pending approvals (the command types its owner approved stay: they are the person's, R-OPS-4), and keeps only its name and owner, so the wiki history and the audit log still say who did what. Names are unique per person and office.
- **R-ADM-4 (M)** Email invitations with expiring links; assignment to offices and role (not for administrators, who work in every office); revoking and deactivating people.
- **R-ADM-5 (S)** Ready-made colleague templates (Windows sysadmin, Linux sysadmin, SQL Server DBA, helpdesk).
- **R-ADM-6 (S)** Cloning colleagues/offices.
- **R-ADM-7 (M)** SMTP configuration from the admin panel (host, port, TLS/STARTTLS, optional authentication, sender) with a test email.
- **R-ADM-8 (M)** **Office colleague**: at most one per office, created, changed, archived and deleted only by administrators from the office in *Admin → Offices* (name proposed as "Guida"/"Guide", role, instructions, any model profile, whoever holds it). It leads the colleague list of everyone in the office, web and Telegram, as if they had created it, and each person talks with it in private conversations nobody else reads. Whatever its profile allows, it only reads the wiki (`wiki_search`, `wiki_read`): no commands, MCP tools, wiki changes, review proposals or private notes, and it is never used to file documents or for the critical reading. Fixed instructions, which an administrator's own only add to: never make things up; facts about the company only from the wiki, citing the pages, and otherwise say it is not there and point to an office manager or an administrator; general knowledge allowed but stated as such. It does not depend on who created it: it stops only when its profile is deleted, and then administrators see that it needs one while the others read that it is not available at the moment. Archiving hides it from everyone and keeps the conversations; deleting it deletes everyone's conversations with it, after a confirmation.

### 5.2 Access and sessions (AUTH)
- **R-AUTH-1 (M)** Email + password and/or magic link sign-in; persistent session ("remember me") with refresh. A page opened while signed out (a link from Telegram or an email, or the page open when the session ended) opens again after signing in; signing out on purpose returns to the home.
- **R-AUTH-2 (S)** Passkeys (WebAuthn).
- **R-AUTH-3 (S)** Mandatory 2FA for administrators and office managers.
- **R-AUTH-4 (L)** Company SSO (OIDC: Entra ID, Google Workspace).
- **R-AUTH-5 (M)** List and revoke active sessions.
- **R-AUTH-6 (M)** Change your own password (current password required); other sessions are signed out.
- **R-AUTH-7 (S)** Passwords reset by an administrator, who never learns them. In *Admin → People* an administrator resets anyone's password, other administrators and themselves included: the person's sessions end at once (an administrator resetting their own keeps the session in use) and they receive a one-time link, valid 24 hours, to choose a new one, which signs them in; the link is shown to the administrator only when the email does not leave (once it has left the administrator never sees it), a new link replaces the previous one, and a disabled person gets none. When no administrator can sign in, `orlok-reset-password --email <address>`, run in the app container, sets a random password, prints it once and ends every session of that person. Every reset goes to the installation log. After any password change (from a reset link, from the server command or from *Account*, R-AUTH-6) the person receives a security notice by email, without links, saying how it was changed and to contact an administrator if they did not ask for it; when the email does not leave, the change still stands. There is no self-service "forgot password": the sign-in page says to ask an administrator.

### 5.3 User area and chat (CHAT)
- **R-CHAT-1 (M)** Responsive web (desktop + mobile), installable as a PWA.
- **R-CHAT-2 (M)** Offices → colleagues → conversations view; streamed answers.
- **R-CHAT-3 (M)** Attachments (files, images) as input for the colleague.
- **R-CHAT-4 (M)** Clear display of tools used, commands and output (expandable). A running command shows how many lines it has written so far, so a person can tell it is not stuck; the output itself shows once it ends. A command that ran without asking because the person always allows its type says so, quietly ("always allowed: <type>").
- **R-CHAT-5 (M)** Approve/reject actions directly in chat (buttons), also on mobile.
- **R-CHAT-6 (S)** Shared office conversations (several people in the same thread).
- **R-CHAT-7 (M)** Notifications (web push / email) when an intervention ends or approval is requested.
- **R-CHAT-8 (S)** Handing a problem over to a colleague in another office (handoff with context).
- **R-CHAT-9 (M)** **Email** channel: a dedicated mailbox read by a colleague (e.g. helpdesk); replies in the same thread; sender recognized as an invited person.
- **R-CHAT-10 (M)** **Telegram** channel: conversation, notifications and approvals through a bot; Telegram users linked to Orlok people. One bot for the installation (token from @BotFather, set in *Admin → Email*), read by long polling so nothing is exposed; each person links their own account from *Account* with a one-time link valid 15 minutes; private chats only. Messages go to the person's own colleagues and the colleagues of their offices (R-ADM-8) (`/colleague` chooses, `/new` starts a conversation, `/conversations` continues or deletes an existing one after a confirmation), in the same conversations as the web app, and follow-ups reach Telegram too. Approval notifications carry "allow once", "deny" and, when the command has types to remember, "always allow" buttons (a plan: "approve the plan", "deny" and "approve and always allow" with its steps' types), with the same meaning as in the app and checked again against the person each request is for; MCP tools and what is approved once each time are decided in the app only.
- **R-CHAT-11 (M)** **Microsoft Teams** channel: bot in the company tenant for requests and replies.
- **R-CHAT-12 (M)** One logical conversation regardless of channel: same policies, same audit, same memory.
- **R-CHAT-13 (M)** An answer belongs to the server, not to the page that asked for it: closing or reloading the page does not stop the colleague, a page opened later follows the answer still being written, only Stop ends it early, and a conversation never has two answers running at once.
- **R-CHAT-14 (S)** **Conversation tabs** (on a computer; a phone keeps the list alone): every conversation opened with a colleague, from the list, a link or the resume, opens as a tab and stays until its tab is closed; the tabs are per colleague and remembered by the browser only. "New conversation" shows a provisional tab that becomes the conversation at the first message. The open tab groups a "⋯" menu (rename, delete) and its close button in a chip, so closing stays one click; on a phone the same menu sits beside the list. Tabs are reordered by dragging them, or with Ctrl+Shift+← / → on the tab in focus, and the order is remembered; the context meter sits under the message box, on a phone too; closing the tab, or deleting its conversation, moves to the tab on its right, else on its left, else to a new conversation. A conversation deleted elsewhere loses its tab. While an answer is being written the other tabs, the list and "New conversation" stay free: leaving the conversation stops watching its answer, not the answer (R-CHAT-13), and coming back follows it again; only the answering tab cannot be closed until it ends, and nothing can be switched in the moment a new conversation is created at its first message. A tab not in view shows a red dot while its conversation has a command or a plan waiting for the person's approval; it goes as soon as it is decided, here or elsewhere (Telegram, another page). The list of conversations marks the waiting ones as "Title ●", and its closed menu shows a red dot while any conversation of the colleague waits, open in a tab or not: the list of conversations says which ones wait. Nothing is asked for again while a request only waits: the server tells the person's open pages as soon as a request starts waiting and whenever it stops (decided in the app, in another window or on Telegram, stopped, or cancelled by a profile change), and the commands of a conversation are asked for again only while one is queued or running.
- **R-CHAT-15 (S)** **Message box and queue**: the message box grows with its text up to about ten lines, then scrolls, and has no grip to drag. On a computer Enter sends and Shift+Enter starts a new line, with no send button; on a phone, whose keyboard has no Shift+Enter, Enter starts a new line and a send button sends. While an answer is being written Stop sits inside the box, and what is sent meanwhile is **queued**: it waits above the box as "Queued", each message with a pencil that takes it back into the box to change it and a × that drops it (its attachments too), and when the answer ends all the queued messages go together as one message, separated by a blank line, with their attachments (at most as many as one message takes). Stop gives the queue back to the box instead of sending it, since it followed an answer cut short. The queue is kept by the open page, per conversation: one queued in a tab left meanwhile goes when that tab is opened again, and closing or reloading the page loses it.

### 5.3b Interface and themes (UI)
- **R-UI-1 (M)** Admin and user area share one design system: modern, functional, dense but readable; responsive on desktop and mobile. The header holds the search button and a personal menu, a circle with the person's initials, with their name and role, the account, language, theme, the administration for administrators and signing out; language and theme open their list in place of the menu, with a way back. The sign-in page keeps its own language and theme choice.
- **R-UI-2 (M)** User-selectable themes, one per colour family so they are told apart at a glance: **Catppuccin Latte**, **Rosé Pine Dawn** and **Tokyo Night Light** (light), **Catppuccin Mocha**, **Tokyo Night**, **Nord**, **Gruvbox**, **Everforest**, **Kanagawa**, **Matte Black** (dark), plus "follow system" (Latte / Mocha).
- **R-UI-3 (M)** Theme choice remembered: stored in the user profile (applies on every device) and locally so it is applied before load with no flash of the wrong theme; the sign-in page honors it too.
- **R-UI-4 (M)** Themes defined only through color variables (tokens), never hard-coded colors in components; text contrast at least WCAG AA in every theme.
- **R-UI-5 (S)** **Keyboard**: whatever the keyboard reaches shows a focus outline in the theme's colour. The arrow keys, Home and End move the focus between conversation tabs, Enter opens the one in focus and Ctrl+Shift+← / → moves it; Tab enters the strip on the open tab and leaves it at once. A **command palette** opens from any page with Ctrl+K (⌘K on a Mac) or the search button in the header. It finds commands (those of the colleague and the office in view first, then each office's wiki, the workspace, the account, the administration sections for administrators, theme and language), colleagues, the open colleague's conversations and the pages of the wiki of the office in view (by title and full text); case and accents do not count. The arrows choose, Enter opens, Esc or a click outside closes it and gives the focus back. Approvals are never decided from it. Direct shortcuts for frequent actions are still to be decided.
- **R-UI-6 (S)** Adjustable chat width (narrow, wide, full width) and alignment (center, left), remembered on the device, set from one menu in two sections in the conversation's toolbar.

### 5.3c Languages (I18N)
- **R-I18N-1 (M)** Multilingual interface: **English** as reference and default language, complete **Italian**; adding a language only requires a new translation file, no code changes.
- **R-I18N-2 (M)** Language chosen by the user and stored in the profile (applies on every device); before sign-in detected from the browser and selectable on the sign-in and setup pages.
- **R-I18N-3 (M)** Installation default language, set during first-run setup: used for new users, invitations and emails.
- **R-I18N-4 (M)** APIs return stable error codes (with a technical English message); text shown to users is always translated by the interface.
- **R-I18N-5 (M)** virtual colleagues answer in the language of the person writing, unless the colleague is configured otherwise.
- **R-I18N-6 (S)** Dates, times and numbers formatted according to the user's language.
- **R-I18N-7 (S)** Product documentation in English and Italian.

### 5.4 Models and providers (MOD)
- **R-MOD-1 (M)** Provider configuration: Anthropic, OpenAI, Ollama, OpenAI-compatible endpoints; encrypted keys.
- **R-MOD-2 (M)** Colleague profiles: a model and a mode (deny, ask, full access, yolo: R-OPS-4), each combination once; after creation only the name changes. Every colleague works with a profile, there is no default one. Administrators grant profiles to people (and in invitations), themselves included, and a person's colleagues use only the profiles granted to them; a profile can be deleted once nobody is granted it. The office colleague is the exception: an administrator gives it any profile, and when that profile is deleted it stops until another is chosen (R-ADM-8). Connection test from the admin panel.
- **R-MOD-3 (S)** Automatic fallback to an alternative profile on errors/unavailability.
- **R-MOD-4 (S)** Token and cost tracking: every model call the server makes is written to a ledger with who it was for (office, person, colleague, conversation), what for, the tokens the provider reported and what they cost at the prices of that moment; a provider is billed per token (prices per model, set by administrators) or included (local models, subscriptions), and a call whose price is not known is *unpriced*, never zero. Monthly spending limits for the installation, an office or a person, checked before every model call, with a warning threshold; administrators are notified once per limit and month. *Admin → Costs* shows the month by office, person, model and purpose, never by colleague (R-ADM-3).
- **R-MOD-5 (L)** Data routing rules: sensitive offices/topics only on local models.
- **R-MOD-6 (M)** Context window per profile (read from the provider when it publishes it): a turn is measured before it is sent, tool output and attachments are shortened, the oldest messages are summarized, and a prompt the provider refuses for its size is recovered once. Nothing is ever silently dropped.

### 5.5 Memory / wiki (MEM)
- **R-MEM-1 (M)** One wiki per office: markdown pages with frontmatter (type, sources, updated by/when), links between pages, index and log.
- **R-MEM-2 (M)** Private notes per colleague (preferences, working context), separate from the shared wiki: the colleague keeps them with `notes_write` (whole text, at most 4,000 characters, never secrets) and reads them at the start of every conversation with its owner, who sees and edits them in the colleague's settings; nobody else sees them. The office colleague keeps none, since everyone in the office would share them (R-ADM-8).
- **R-MEM-3 (M)** **Ingest**: uploaded documents and closed conversations/interventions → update existing pages or create new ones, citing sources. Colleagues change part of a page with an exact replacement (`wiki_edit`, saved only when the old text appears exactly as many times as stated); a whole-page rewrite that keeps less than 70% of a page over 1,500 characters is refused unless the colleague says the cut is intended, and a rewrite that drops links, headings or literal values (addresses, dates, commands) says which, so they can be put back. A new page whose title is close to existing ones names them. Every revision written by a colleague records where it came from: the conversation and the commands it ran there before writing, or the document being filed. A colleague working for someone who may not edit the wiki writes nothing: its change is proposed in the review queue, and an office manager applies it on the revision it was written against, or dismisses it.
- **R-MEM-4 (M)** **Query**: the colleague consults the wiki before answering (full-text + vector search + links). Word search is ranked in the app (BM25-style, normalized by page length; 6-letter prefixes; exact bonus for long identifiers; addresses, host names and codes searched whole; 2-3 letter terms only as whole words or endings) with synonym groups: built-in Italian/English IT vocabulary plus each office's own, edited by its managers. Retrieval changes are measured with `wiki:eval` (recall@1, recall@k, MRR on questions with their expected page) before they are made, and on turns of real conversations (`--turns`: expected pages found, precision, off-topic pages per turn, no page for small talk). People write to colleagues as they talk ("verifica ora", "l'ha detto il tecnico"): before answering, a model reads the latest message with the conversation around it and writes the search, or none for small talk (Admin → Models → Wiki search: the colleague's own model by default, another profile, or off, in which case the message is searched as written, a short follow-up together with the question before it; any failure falls back to that). The search keeps the rarest words of the query wherever they stand, a page counts only if it holds a word few pages hold, meaning adds to pages the words found (one page found by meaning alone only when it stands out), and pages far below the best are left out: 0 to 5 pages, not always 5. Of a long page the colleague receives its beginning and the run of lines where the words of the question gather, not only its first characters. Under the answer are shown the pages it used, read or cited; the pages it was given are kept on the message to check what the search brings.
- **R-MEM-5 (M)** Strict isolation: no access across offices, neither read nor write.
- **R-MEM-6 (M)** Version history for every page; restore.
- **R-MEM-7 (S)** Periodic **lint**, every night for every office and after each filed document: contradictions, orphan pages, stale information, duplicates → human review queue. Checks without a model: a host given different private addresses in the same /24 by different pages, verifications older than a year, relative dates ("currently", "yesterday") without a date on the line, hosts mentioned in 4+ pages without a page of their own. A health score per page (100 minus penalties) lists the worst pages first. Every review item says what to do, and can be fixed with a virtual colleague: a conversation opens with the request already written, the colleague lists the open items (`wiki_review_list`), fixes them once the person agrees and closes them in their name (`wiki_review_close`, only for people who may edit the wiki).
- **R-MEM-8 (S)** Verified procedures: a successful intervention can become a reusable runbook.
- **R-MEM-9 (S)** Wiki editor and graph in the web app (read for everyone, edit for office managers).
- **R-MEM-10 (L)** Company-wide wiki shared across offices (read-only, content promoted explicitly).
- **R-MEM-11 (M)** Initial wiki import from a markdown folder and from Joplin (Data API), mapping notebooks → sections and preserving internal links whichever way the export writes them: relative or root paths with or without `.md`, encoded or not, `[[wiki links]]` by file name or title (Obsidian), names ending with a Notion id (dropped from titles and sections), and links an export could not resolve (Joplin's `undefined` and `:/id`), matched by their text against the imported titles or left as plain text.
- **R-MEM-12 (S)** Wiki export as a markdown folder with frontmatter, Obsidian-compatible.
- **R-MEM-13 (S)** Outdated knowledge is kept and marked, never deleted: a page has a status (current, superseded, retired, historical) and the day it was last verified on the real systems; a statement replaced inside a page is kept with `> **Superseded (date):** old → new`. Search ranks outdated pages after current ones, and colleagues see their status. Colleagues write dates in full; two statements with different numbers or dates are never duplicates.
- **R-MEM-14 (S)** Critical reading on request: one of the office manager's own virtual colleagues rereads a few pages (5) next to their two most related pages and reports at most two certain contradictions per page, each with a quote that must really be in the page. A page is read again only after it changes. Findings raised by a model and closed by a person never come back.
- **R-MEM-15 (S)** Ingest outcome: before filing, the analysis classifies what a document brings (new, update, contradiction, nothing); a document that brings nothing is not filed, and the outcome is recorded on the document.
- **R-MEM-16 (S)** Proposals from quiet conversations: an hour after the last message, a conversation of at least 4 messages from the person that did not write to the wiki is read once by its colleague, which proposes at most 3 pieces of durable knowledge. Only the person who had the conversation sees them, in the conversation, and saves each one to the wiki (filed like a saved answer) or lets it go; nothing is written without them.

### 5.6 Operations (OPS)
- **R-OPS-1 (M)** One host registry for the whole installation, kept by administrators: name (unique whatever its case), OS, address, port, tags. A host is the machine and nothing else: the account used on it is the credential of the person a colleague works for (R-OPS-3), not a property of the host.
- **R-OPS-2 (M)** Linux servers via **SSH**; Windows servers via **PowerShell Remoting** (WinRM, http with NTLM or Kerberos message encryption or https with a verified certificate, password credentials) or OpenSSH.
- **R-OPS-3 (M)** Personal credentials (passwords, SSH keys, tokens): each person stores their own in their account and chooses the hosts each one is used on, at most one credential per person per host, and tests it on those hosts, which happens by itself as soon as it is saved. A colleague working for a person reaches only the hosts where that person has a credential, and acts there as that person, so the target systems decide what it may do. Colleagues use credentials without seeing them, never in chat text or in the wiki; asked to work on a host where the person has none, a colleague tells them to add one in their account, never in the chat. Tokens are stored but not used yet. A person's credentials are deleted when they are disabled.
- **R-OPS-4 (M)** What a colleague may do follows from the person it works for: hosts come from that person's credentials (R-OPS-3), the runner and the office's MCP servers are there in every mode but deny, and how it runs commands is the mode of its profile (R-MOD-2): deny (none), ask (reads and the command types the person approved run, the rest needs approval), full access (no approvals, forbidden commands stay forbidden), yolo (no approvals, forbidden commands run too). There is no per-colleague policy. A command is split into pieces, each with a type (the program and up to three words, `systemctl restart`, `net user`, `Restart-Service`; `sudo` is part of the type, a file written with `>` is a type of its own); it runs when every piece is a read or an approved type, otherwise only the missing types are asked. "Allow always" approves them for the person it was asked for only, with all their colleagues, on every host and on the runner. A PowerShell command is read as a script: variables, expressions, `if`, `foreach`, `for`, `while`, `try`, hashtables and the functions it defines are followed into, and every command found inside them is a piece like the others; an expression may call only .NET methods and types known to compute or read. A command that cannot be read to the end (substitutions in a POSIX shell, interpreters, scripts, remote shells, other .NET methods, property and special-variable assignments, `switch`) or that reads a secret file is approved once each time. Why a command asks, is approved once only or is refused is shown to people as a plain sentence in their language. Each person sees, turns off and removes their own types; an administrator sees them per person and can turn one off, and then only an administrator turns it on again. Only the person an intervention was asked for sees it, decides it and stops it, administrators included.
- **R-OPS-5 (M)** Interventions as durable jobs: they continue if the user disconnects, have status, timeout and a stop button. A command running when Orlok restarts has an unknown outcome: it is never run again by itself, its plan stops, and the person and the colleague are told to check the state before retrying.
- **R-OPS-6 (M)** "Plan" mode: the colleague proposes the steps; approval of the whole plan or step by step. A whole plan can also be approved with "allow always", which remembers the types of the steps that can be read to the end, as for one command (R-OPS-4); the other steps run that time only.
- **R-OPS-7 (S)** Isolated workspace per colleague (container) for scripts, temporary files, CLI tools. The first version ships a shared **Orlok runner** container (network and CLI tools, no access to the database) used by colleagues as an execution target alongside the hosts (§9).
- **R-OPS-8 (S)** **Client module** (single executable for Windows/Linux/macOS): outbound connection to the server, execution via PowerShell or the local shell.
- **R-OPS-9 (S)** **Consent on clients**: the PC user is notified before an intervention, can see what happens and can stop it.
- **R-OPS-10 (S)** External tools via **MCP** (MCP servers configured per office, used by every colleague of the office). An administrator chooses which of a server's tools colleagues are given: a server with hundreds of tools would otherwise fill every prompt with their descriptions.
- **R-OPS-11 (S)** Automatic inventory: data collected from hosts updates the matching wiki pages.
- **R-OPS-12 (L)** Non-chat triggers: monitoring webhooks (Zabbix, Uptime Kuma), scheduled tasks. (Email as a channel is R-CHAT-9.)
- **R-OPS-13 (L)** Tailscale support as the network to reach clients without the module.
- **R-OPS-14 (dropped 2026-09-22)** **Away mode** per office: an alternative policy profile allowing predefined actions while the manager was away. Built and then removed, see §9.
- **R-OPS-15 (M)** Tool catalog: ready-made external tools (MCP servers) installable per office from the interface in a few clicks, with only the credentials to fill in; adding a tool never requires rebuilding an image or editing files. Each entry explains, in the person's language, how to obtain credentials with the least rights that do the job, asks for them as labelled fields, and lets the administrator choose right there which of its tools colleagues are given (R-OPS-10). Shipped entries include AWS (through the AWS MCP Server) and Proxmox VE.
- **R-OPS-16 (S)** Additional runners registered from the interface (name, address, token, tags): a customer can run a specialised runner container next to the default one, and colleagues choose it as a target.

### 5.7 Product and distribution (PRD)
- **R-PRD-1 (M)** Empty installation: no company data or configuration shipped in the product; everything goes through the wizard (R-ADM-1).
- **R-PRD-2 (M)** Documentation: installation, upgrade, backup/restore, administration, usage; also published on the website (https://orlok.xyz/docs).
- **R-PRD-3 (S)** Public versions and changelog; versioned Docker images; guided upgrades.
- **R-PRD-4 (S)** Colleague and office templates shipped as optional packages, separate from the core.
- **R-PRD-5 (L)** License and activation: the core under the Business Source License 1.1, free for personal and non-commercial use, with each version becoming Apache 2.0 four years after its release; business features in a separate proprietary part unlocked by a license key; companies pay a subscription, priced per host, that covers production use, the business features and support (decision in §9).

Done: online at https://orlok.xyz since 2026-10-09 (static site + contact form, repo `rylos/orlok-web`).

### 5.8 Security and audit (SEC)
- **R-SEC-1 (M)** Immutable audit log: who asked what, plan, approvals, commands, output, wiki changes, credential use. Events that belong to no office (hosts, people's credentials, the command types they approved) form the installation log, which only administrators see.
- **R-SEC-2 (M)** Encryption at rest of credentials and provider keys (master key outside the database).
- **R-SEC-3 (M)** Automatic masking of secrets in output and logs. A Markdown or Joplin import, and the text of an uploaded document before any model reads it, replace what looks like a credential with `[secret removed]` before saving (labelled values, `NAME_PASSWORD=` assignments, passwords in connection strings, JSON Web Tokens, credential rows of tables, keys, tokens, Authorization headers, lone password-like lines); the same detector refuses a colleague's wiki write and masks command output and says how many it removed: notes kept for one person often hold passwords, the office wiki is read by everyone and sent to model providers.
- **R-SEC-4 (M)** Prompt injection defense: content from documents, command output and emails is treated as data; sensitive actions are always subject to the R-OPS-4 rules, never decided by the model alone.
- **R-SEC-5 (S)** Audit export (CSV or JSON Lines, installation and every office, cells a spreadsheet would evaluate neutralized; the export is itself logged); configurable retention (open).
- **R-SEC-6 (S)** Compliance: notice and consent for interventions on employees' PCs (GDPR, Italian Workers' Statute art. 4).
- **R-SEC-7 (M)** The login is rate-limited per account and per address: an installation published on the internet must not let passwords be guessed at the speed of the network, and the limit per address is looser so that one company behind a single public address does not lock itself out.

## 6. Non-functional requirements

- **NF-1** Installation with a single `docker compose up`; documented backup and restore (database + files).
- **NF-2** Multilingual as per R-I18N (English default, Italian, more languages can be added).
- **NF-3** Works without mandatory cloud services (fully offline with Ollama).
- **NF-4** Upgrades with automatic database migrations.
- **NF-5** Initial sizing: tens of people, tens of colleagues, hundreds of hosts.
- **NF-6** Observability: structured logs, health status, basic metrics.

## 7. Stack

- **pnpm** monorepo: `apps/server`, `apps/web`, shared `packages/*`; the client module (R-OPS-8) will be written in **Rust**.
- Server: **Node + TypeScript**, **Hono**, **Postgres + pgvector**, Drizzle ORM, pg-boss for durable jobs, streaming via SSE/WebSocket.
- Models: official provider SDKs (**@anthropic-ai/sdk**, **openai** for OpenAI, compatible servers and Ollama) behind an internal provider-neutral adapter; **MCP TypeScript SDK**.
- Web: **React + Vite + shadcn/ui** (Tailwind, themes via CSS variables), react-i18next, PWA.
- Distribution: **Docker Compose**.

## 8. Phases

1. **MVP**: all **M** requirements → offices, personal colleagues, invitations, chat, providers, basic wiki, servers via SSH/PowerShell with personal credentials, profiles, approvals and audit.
2. **Phase 2**: **S** requirements → client module and consent, wiki lint, MCP, costs and limits, shared conversations.
3. **Later**: **L** requirements → SSO, external triggers, company wiki, data routing.

Approving the exact command, or a whole host, pushed people towards full access; a type is what people mean when they say "yes, restart services". A type covers all its arguments (`rm` covers `rm -rf`): what is catastrophic stays forbidden outside yolo, and what cannot be read to the end is approved once each time instead of having a list of types excluded from "always". The table, the reads and the forbidden commands started from the proposal in the decision document and change as they are used; a remembered type applies only to a command of exactly that type, so changing the table never widens an approval. The exact commands remembered until then were dropped: turned into types they would have allowed more than each person approved (R-OPS-4, R-SEC-1).

A colleague is told what the person can change: on a host where they have no credential, to add one in their account; in deny mode, that its profile allows no commands. A type approves a kind of command, the credential sets the account it runs as, and "allow always" already holds on every host with whatever credential the person has there, so a new account on one host is not a new situation. An account with fewer rights needs nothing either: the system refuses what the account cannot do. To hold someone back, an administrator gives them only deny profiles, disables them or restricts their account on the server; turning their types off only makes them confirm each command again (R-OPS-3, R-OPS-4).

- PowerShell scripts read (2026-10-11, from the first tests, block D1): every small script colleagues wrote for Windows hosts (a variable, a `foreach`, a `try`, a string line, a `.TrimStart()`) could be approved only once, so "allow always" was never offered and approving without reading became the habit. A line is now read statement by statement: assignments are judged by their right side, groups, sub-expressions, strings, hashtables and script blocks are read for the commands inside them, and a function the script defines is read where it is defined, its calls not being types of their own. What an expression may do without being a command is a short list: .NET types for conversions and static values, static and instance methods that compute or read (text, dates, folder listings, in-memory collections); any other method, a property set, `$env:` and the variables that change how commands run, `${C:ile}` paths, `switch`, a function without a dash in its name (an alias of the same name would win) or defined inside a block, `New-Alias`/`Set-Alias` and `Import-Module` still ask once. A sensitive path anywhere in the script makes its file reads once only, so `Get-ChildItem -Filter id_rsa | Get-Content` now asks too. `Out-Null`, `Start-Sleep`, `Join-Path` and `Split-Path` join the reads (R-OPS-4, R-SEC-1).
- "Allow always" for plans (2026-10-11, from the first tests, block F1): a plan was approved only as a whole, so its routine steps asked again every time and "allow always" was never offered for them. A step approved on its own from the plan's card can be allowed always too, and Telegram offers "approve and always allow" for a plan, so the three ways to approve a plan behave alike (R-OPS-4, R-OPS-6, R-CHAT-10).

The user also asked that the server does no work for nothing: while a request waited, the page asked every two seconds for the list of conversations and the commands, and every four for the whole conversation, for as long as the request waited, which can be days. A page whose live connection drops reads everything again when it is back, the commands included. Covered by tests for each way of ending the wait (R-CHAT-14).

- Password resets (2026-10-21, the user's request; R-AUTH-7; migration 0040, runner unchanged): a forgotten password had no way back, and when the only administrator forgot theirs the only one was writing a new hash into the database by hand. An administrator now resets a password from *Admin → People* with a one-time link the person opens, like an invitation (24 hours, sent by email and shown when the email does not leave), rather than a temporary password, so that nobody but the person ever knows it; the sessions end when the link is made, not when it is used, so whoever holds a session is out at once (the old password itself keeps working until the link is used). On the server, `orlok-reset-password` generates a password and prints it once instead of reading one from the keyboard, so nothing lands in the shell history and no interactive terminal is needed; it works for anyone, since whoever can run it can already reach the database, and refuses a disabled person. An option to enable a disabled administrator was weighed and left out: the last active administrator cannot be disabled or demoted (`last_admin`, `self_change_not_allowed`), so one can always sign in. A self-service "forgot password" by email was not chosen: the sign-in page points to an administrator. A notice of the change by email (2026-10-22, the user's request; no migration, runner unchanged) followed for all three ways a password changes, so a change the person did not make does not go unnoticed; it carries no link, like most security notices, so it cannot be mistaken for phishing. The reset link is no longer given to the administrator once the email has left (2026-10-22, the user's check): whoever holds it chooses the password and acts as the person, with their own credentials on the hosts, so an administrator could have done it unnoticed; unlike an invitation's, it is not shown on request, and when it does not arrive the administrator resets again. When the email does not leave there is no other way, and the link is still shown.
- Office colleague (2026-10-22, the user's request; R-ADM-8; migration 0041): the user had to explain the same basic procedure, several steps long, to several people one by one. An administrator can now give each office one colleague that everyone in it finds in their own list and that answers from the wiki, so a procedure is written once and explained by it. It keeps "a colleague never has more rights than the person it works for": it only reads the wiki of the office, which everyone in the office can already read, so it was given no other tool whatever its profile says, and no private notes, which everyone would share. For the same reason its profile is not tied to a person's grants: an administrator chooses any profile and may reassign one when it is deleted, and office managers do not create it (the user's simplification, after weighing that they could pick among their own profiles). Conversations stay private, administrators included. Weighed and not chosen: a template pushed as a personal copy to every member (every person would need a profile, instructions would drift and copies could be changed or deleted) and only writing the procedure in the wiki (it does not help people without a colleague of their own). The user asked that it never make things up; a model cannot promise that, so the fixed instructions, the read-only tools and the cited pages make it as close as can be, and general knowledge is allowed only when stated as such. Recording the questions the wiki could not answer was set aside over privacy: a later step may let a person report, of their own choice and with the text they decide, that something is missing, into the review queue.
